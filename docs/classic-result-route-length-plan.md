# Classic result route-length implementation plan

Status: implemented in the working tree and exercised in the packaged Mac app against the championship series. Local acceptance and regression evidence is recorded below. Not committed, published, or released. The implementation notes describe the first conservative release boundaries; the remaining sections retain the original design rationale.

## First implementation: operational notes

- When any assigned control (including the assigned Beacon) is absent from the retained downloaded punches, human-readable results show `Estimated effective route length: n.nn km (missing punches)` instead of an ideal-order comparison. This is a runtime presentation derived from the existing validated snapshot, ignored-punch indexes, and assignments: no terrain recalculation or native-file migration is required. Extra or repeated punches alone do not trigger this wording, and raw scoring/status is not used as a substitute for control identity. Distances, category headings, private metadata, and machine-oriented comparison fields are unchanged.
Ignored-control update validation: packaged Mac build 1.0.42k processed the championship series to 55/55 saved estimates. SI 134 remains in the downloaded readout and scoring data, but its estimated route now measures 7.39 km (2.66 km above ideal). Retained-source replay and all export adapters passed; the new estimate exactly equals a calculation-only copy with that punch removed, and all 54 previously valid estimates are unchanged. The full gate passed 828 desktop, 632 shared, and 225 Android tests (1,685 total); 27 dedicated Classic tests cover the updated policy. A separate pre-update native series backup is retained under `output/classic-route-validation/championships-before-ignore-policy.roseries`.

- Unknown or ambiguous downloaded controls are ignored for estimated route length only, exactly as if those punches were absent. This includes an unresolved SI identity or missing/ambiguous location for an extra downloaded control. Ignored punches do not participate in timestamp validation or ideal-order comparison. Their indexes and the `ignore-unresolved-v1` punch policy are retained privately with the snapshot; full raw-input fingerprints still invalidate the estimate after corrections or control-catalog changes. Raw readouts and scoring are unchanged. A previously unavailable result is retried on the next requested analysis; existing successful strict-policy estimates remain valid. Required ideal-course geometry, Start/Finish, and sampled terrain coverage remain strict requirements.
- Human-readable desktop results use `Estimated effective route length: n.nn km (ideal order)` or `Estimated effective route length: n.nn km (difference from ideal order: m.mm km)`. The signed difference is calculated from integer meters before rounding both displays to two decimals; a tie is not relabeled as an ideal-order match. A negative difference can reflect missed controls, not a better complete course. The detailed comparison state remains in machine-oriented extended exports.
- Analyzed category headings include the result count and certified analysis ideal, e.g. `W45 (1) - Ideal route: Fox2-Fox3-Fox1 (EL: n.nn km)`. Start, the fixed terminal Beacon, and Finish are omitted from the heading order but included in its length. The order is recovered against the saved reference fingerprint using accessible geometry, bounded to the existing eight-control limit and cached; it does not sample elevations or rerun optimization. The runtime heading is not serialized. Protected or ambiguous geometry suppresses the order instead of exposing or guessing it, while the saved ideal EL remains available. Unanalyzed categories and shared-default/Android reports retain their existing headings.
- Results → **Estimate effective route lengths…** starts a one-shot background batch or enables processing of new/corrected downloads for the selected event. For an open native `.roseries`, the dialog can include every Classic member. No Android worker, database migration, or export option is added. Android-originated results can be processed after transfer and course geometry/elevation preparation on desktop.
- Each category's ideal order is verified automatically through the existing Course Analyzer exhaustive search. The analyst does not need to run Course Analyzer manually. This creates a separate, explicitly labeled **analysis ideal** reference; it does not silently overwrite imported course design data, its saved ideal order, or its displayed design length. Differences from a previous course effective length are retained in the private reference metadata.
- The version-1 extension lives at `EventProjectFile.desktopRouteAnalysis`, alongside native results. Existing schema-6 readers can ignore it. Desktop native copies retain it; Android Room/import/export workflows do not promise retention. Keep the desktop native copy authoritative for this extension.
- The first version deliberately invalidates conservatively: course/control identities, protected payload replacement, and relevant punch timing/order changes can require recalculation even if an equivalent route might be provable. Ordinary result scoring, competitor names, and race names do not invalidate the calculation. Cross-platform ID rewrites are handled by fresh desktop processing, not speculative metadata remapping.
- Terrain data and source ordering are frozen for an enabled processing session. Content-addressed copies are retained under the desktop elevation cache's `route-analysis-sources` directory, with digests recorded in each reference. Saved values remain viewable/exportable without those files or a password. Reproducing a historical computation requires those retained terrain sources plus the original course geometry; terrain source bundles are not embedded in the native race/series file. This storage is local and is not automatically uploaded or synchronized.
- Metadata-only atomic recovery checkpoints live under `route-analysis-recovery`, keyed by event identity/path. Recovery validates saved native inputs before merging; it cannot recover otherwise-unsaved readouts. A completed clean event can save analysis-only data automatically. A dirty event keeps the existing unsaved indicator and asks the user to save normally; it does not auto-save unrelated edits. Native series writes are coalesced per completed member batch, not per competitor.
- Work is bounded to one background calculator, with bounded sampled-leg and full-route metric caches. Course references and repeated orders are reused during continuous processing. Switching tabs does not stop work; leaving its owned event/series context or closing it cancels work and prevents detached late writes. Continuous completion uses the persistent status area, not a modal alert for every card.
- Desktop CSV, split CSV/PDF, TXT, HTML, Radio-Oracle report XML/PDF, and desktop public-site JSON/page/downloads receive only the validated public projection. Reports label the verified reference as `analysis ideal`. Shared exporter defaults remain unchanged. ARDF/final/live JSON, ARDFEvent CSV, IOF, ROBIS, Android backups, and all Android result exports remain compatibility profiles without the extension. No standards-facing extension or standards PR is included.
- While a desktop file export is pending, choose **Export available now** or **Wait for captured results**. Waiting is asynchronous and uses the original result watermark; later downloads are excluded. Corrections, deletion, or course changes require a fresh export request. Existing remote website publication remains explicitly user-triggered. An already running local results server refreshes through its existing debounce mechanism.
- Unsupported reference geometry is reported rather than guessed: a unique explicit Start, Finish, assigned Beacon, and resolvable assigned controls are required. Mandatory waypoints and more than eight permuted controls are refused. Known extra/missing/repeated controls retain a `Different control set` comparison state; unresolved downloaded controls are ignored as described above. Missing terrain coverage, invalid coordinates, or backwards retained control-punch times remain unavailable. Alternate orders may tie; shorter-than-reference results are retained, never clamped.
- For repeatable copy-only processing: `just classic-route-lengths input.rom.json output.rom.json`. An optional Race Password is supplied using `RADIO_ORACLE_ROUTE_PASSWORD`, never as a command-line password argument. Do not point automation at a file simultaneously being edited by the desktop app.

Synthetic artifacts remain under `desktopApp/build/reports/classic-route-analysis/`. Real-data acceptance artifacts are under `desktopApp/build/reports/classic-route-live/verified-exports/`; a durable pre-analysis archive backup is under `output/classic-route-validation/championships-before-analysis.roseries`. The user explicitly authorized testing and saving the championship series on 2026-09-05. The acceptance hook itself is read-only toward its source archives.

## Outcome and scope

Add an optional desktop background service that calculates and saves each Classic competitor's estimated effective route length using the same straight-leg sampling, elevation data, complete-route climb calculation, and rounding as the course's ideal reference. The user can process existing results in a batch or enable ongoing processing of newly downloaded results during an event. Completed values appear in desktop result views and are ready for desktop export without recalculation, elevation files, or a course password.

Initial eligibility is explicitly `race.raceType == RaceType.CLASSIC`, covering both Classic 2m and Classic 80m. `SHORT`, `SPRINT`, `FOXORING`, and `ORIENTEERING` are excluded. Youth categories within a CLASSIC race remain eligible. A mixed Race Series processes only selected Classic members.

This feature is desktop-only. Android downloading, storage, displays, exports, and publication retain their existing behavior and do not calculate or export these lengths. No Android Room migration or Android feature UI is planned. Shared code may gain opt-in data/formatting helpers needed by desktop, but all existing caller defaults must preserve Android behavior. Users must retain the desktop event/analysis copy for this extension; preservation through Android is not promised.

Build this in small stages. Enable one-shot background batches before enabling the continuous queue. Both modes must pass persistence, input invalidation, cancellation, and export compatibility gates. Existing scoring, ranking, points, SI downloading, transmitter waits, estimated times, and ideal-order search algorithms keep their behavior; the new queue receives a notification after an accepted result update.

## Calculation contract

1. Use the existing `DesktopCourseRouteSampler` and `DesktopCourseRouteMetricsCalculator`. Keep numerical code and background orchestration on desktop.
2. Preserve current defaults: 25 m straight-leg sampling, Haversine horizontal distances, 50 m distance-based median smoothing, 2 m climb prominence, and effective length equal to horizontal length plus ten times climb.
3. Assemble the entire sampled route, dropping repeated junction samples exactly as the existing sampler does, before smoothing and calculating climb. Cache sampled directed legs, never independently calculated leg climbs: smoothing and prominence depend on the joined route.
4. Keep intermediate values as doubles. Match the existing saved-course convention: round horizontal length and climb individually to integer meters, then derive effective length from those rounded components. Test this explicitly against rounding the final double, which can differ.
5. Resolve recorded CONTROL punches in recorded order, bounded by the result's Start and Finish. CHECK/readout records do not become route stops. Preserve meaningful revisits and known extra controls regardless of scoring status. Consecutive repeated punches at the identical location can be normalized only through a documented shared rule applied equally to reference and competitor routes.
6. Resolve physical locations using course/category identity first, then the existing IOF ID and label/type matching strategy. Extract the needed resolver behind its existing IOF facade and add ambiguity detection for the new analysis; preserve current IOF output. Resolve extra known controls from the race catalog and available protected course geometry, including their provenance.
7. Include Start, terminal Beacon, Finish, and any supported mandatory non-punched course objects consistently with the reference's route construction. Do not insert missing punched controls, infer an unrecorded Beacon visit, move recorded controls into the ideal order, or guess how an imported corridor/waypoint applies to a changed order. Unsupported course geometry is a preflight failure for that category.
8. Require real elevation coverage for every sampled point in a comparable calculation. The existing endpoint-interpolation fallback is not silently allowed for this feature. Report unavailable coverage separately from a numerical result.
9. A full ideal-order match must produce exactly the reference's published effective length. Establish that equality by common inputs and the same rounding, and test it; copying the saved ideal value must never conceal a recalculation mismatch.
10. A different complete order can tie the ideal. A shorter value is retained honestly for review, never raised to the ideal. Equal-or-longer is a mathematical expectation only if the reference is a verified minimum under the same full-route objective and constraints.

Use the route as downloaded, including resolvable known extra visits, but omit unknown or ambiguous downloaded controls and their timing information for route estimation. Leave routes without a reliable Start/Finish or reference geometry uncalculated. A competitor who finished but missed assigned controls may have a calculable route; retain its distance with a `different control set` comparison state and a signed difference from ideal. DNF or disqualification status alone is not a substitute for checking the actual route evidence.

## Stage 1 — Establish reference behavior and characterization tests

Inspect the actual Classic reference producers: imported course data, generated courses, calculated analyzer routes, and shared-course propagation. Record their sampling, cached/fallback elevation use, rounding, extra course objects, and minimum-search evidence before changing them.

Important existing boundaries:

- `DesktopCourseAnalysisApplier` persists the sampled route and integer length/climb but does not currently persist a complete calculation/elevation identity.
- `ProtectedCourseInfo.sourceSha256` identifies the imported source file; it is not an elevation-cache digest and must retain its current meaning.
- `DesktopVenueElevationCache` chooses sources dynamically by priority, resolution, and date. A new analysis must use a frozen selection.
- The generator's subset search can optimize sums of independently measured edges, whereas final route metrics use whole-route smoothing. Even a search called exhaustive does not prove minimality under a different objective. Use full-route exhaustive enumeration as a small Classic test oracle; do not change the production search as part of this feature.
- An imported route can share the ideal order yet contain non-straight geometry. Order equality alone cannot certify metric equality.

Add deterministic synthetic Classic fixtures with three to five foxes, Start, Beacon, and Finish. Include a hill between equal-elevation endpoints, a hill crossing a leg junction, a repeated location, and a rounding boundary. Characterize the current sampler and metrics before adding adapters. Use anonymized data for checked-in fixtures; do not check in championship personal information or protected coordinates.

Gate: ideal metrics, existing analyzer/generator behavior, and existing outputs are unchanged; supported and unsupported Classic reference shapes are documented.

## Stage 2 — Freeze provenance and certify a comparable baseline

Introduce an immutable calculation context for one course reference. Record a method version, sampling/filter/rounding parameters, ordered physical reference stops, reference geometry/profile digest, full-precision and published reference metrics, course-input digest, and search-certification state.

For elevations, freeze the ordered cache selection and immutable loaded data at job start. Record the content digest, source identity, resolution, and interpolation/fallback policy for every contributing cache. Hash each source once per job. Avoid recording machine-specific paths as the identity. Persist source metadata and calculation inputs inside protected course data where they disclose course geometry; public exports receive only approved result scalars and labels.

The lightweight context and hashes make saved results auditable, but hashes cannot recreate a missing terrain surface. Preserve the exact cache files, or a lossless venue subset sufficient for all supported Classic legs, in an explicitly retained analysis bundle. Use the existing cache format and protected/private storage boundaries. Do not automatically copy a large DEM into every result or Race File. Document how to retain the bundle for later recalculation; ordinary result exports never require it.

For newly calculated/saved ideal courses, capture this context alongside the existing protected course data without changing metric formulas. Preserve it through course mapping, equivalent-category propagation, renumbering, and encryption changes where the underlying inputs remain equivalent. Do not assume categories with matching memberships already have identical saved metrics.

For an existing course without provenance:

- Reconstruct its supported straight reference and compare the complete stored sampled profile, geometry, and metrics against the frozen source, using explicit tolerances only for profile comparisons and exact equality for published integer metrics.
- Matching the old ideal profile is evidence, not proof that the old terrain source was identical on alternative legs. Mark historical provenance as unverified unless the original source and method can actually be established.
- If historical provenance cannot be established, offer a separate, previewed baseline-establishment operation. It recalculates the saved reference order and all selected competitor routes from one frozen source, shows any changes to category ideal length/climb, and requires the organizer to accept that new baseline. It does not silently change the ideal order or claim to recover the historical DEM.
- If the organizer retains the original reference without sufficient evidence, leave comparable result calculations unavailable with a concrete reason. Never mix legacy saved components with newly sampled alternatives and label them equivalent.

Gate: a known source/method reproduces the reference exactly; changed source bytes, profile, parameters, or reference geometry prevent certification. Missing data never triggers endpoint-only effective lengths.

## Stage 3 — Persist desktop snapshots without changing Android behavior

Use a versioned desktop analysis extension associated with the native event, containing snapshots keyed by race/result identity and semantic input digest. Prefer optional private metadata at the Race File envelope level, carried inside each native Race Series member, rather than fields on the core `EventResult` or Android entities. A snapshot stores horizontal length, climb, effective length, calculation time, context identity, ideal-match/comparison state, and the reference effective length used for comparison. Share the larger provenance context per course/analysis revision instead of repeating it per competitor.

Represent persisted validity separately from worker state. Persist `current`, `stale`, or `unavailable` with a concise reason, with absence meaning `not calculated`; the session also exposes `queued`, `calculating`, and `paused`. Desktop exporters consume only current snapshots. Preserve a previous snapshot for audit when it becomes stale, but never export it as current. A failed rerun leaves a still-valid previous snapshot intact; an input change invalidates it independently of rerun success.

Before settling the encoding, prove with the existing Android-compatible codec/import path that the optional metadata is permitted under the current core schema and does not change core event semantics. The observed Race File schema is 6; recheck at implementation. Version the analysis extension independently only where the existing additive-metadata contract allows it. Do not silently waive schema rules or raise the core schema so existing Android imports stop working. If an embedded extension cannot meet both constraints, use a desktop-managed companion file alongside the native event/archive, with explicit copy/Save As/bundling support, and document that storage decision before exposing the feature. This encoding gate is a prerequisite, not an assumed compatibility claim.

Verify preservation through:

- Desktop standalone Race File write/read, including encrypted and plaintext course data.
- Desktop Race Series member save, archive write/read, copy, Save As, import, and export, including companion packaging if required.
- Desktop result replacement, copy, category reassignment, unmatched readout assignment, and legacy import paths.
- Existing Android import of the core event and unchanged Android exports, with the desktop analysis omitted. An Android round trip is allowed to drop the extension and must never make missing metadata appear current on return.

Keep desktop persistence and export projections separate. Legacy Android-shaped backup JSON currently reuses final-result DTOs; its default projection must stay unchanged. Native desktop save/reopen retains full snapshots/context; Android-compatible transfer and legacy backup profiles omit the extension. Returning results from Android can be reconciled with a retained desktop analysis copy only when result/course identity and every relevant semantic digest agree; otherwise queue fresh work or show `not calculated`. Do not rely on arbitrary unknown-field preservation in Room.

Gate: snapshots and context links survive every desktop native round trip, while Android imports/exports and legacy shared-export defaults remain compatible. Existing records retain all prior fields and ranking behavior. Existing package fingerprints cover only limited series metadata, so add explicit snapshot/context assertions rather than treating a matching package fingerprint as proof.

## Stage 4 — Enforce the persisted-result lifecycle

Implement one desktop validity/accessor API for result displays and exports. Its input is the result plus the current race/course revision context; it never loads terrain or decrypts geometry during export. Supply only its validated public projection to shared formatters through explicit opt-in arguments. Validate cheap semantic fingerprints at the boundary as a backstop to targeted invalidation in desktop editors/importers.

| Change | Expected behavior |
| --- | --- |
| Punch code/order/addition/removal, changed route boundaries, replacement download | Invalidate affected result unless semantic route inputs are provably unchanged |
| Result category reassignment, race type change | Invalidate affected result; reject non-Classic eligibility |
| Control location/role, Start/Finish/Beacon, required membership, reference order/profile/metrics | Invalidate all dependent snapshots, including extra controls used from other categories |
| Course reimport, replacing protected payload without equivalence evidence | Invalidate dependents |
| Name, club, award, place, score, manual status, transmission sent flag | Retain metrics if route inputs are unchanged; reevaluate comparison eligibility where necessary |
| Time correction with the same ordered route and same boundaries | Retain metrics; update validity if the correction changes which punches belong to the route |
| Display renaming, equivalent SI renumbering, ID remapping, encryption/password change | Retain only when semantic identity/context is preserved; test each round trip |
| New elevation files installed or app upgraded | Retain historical snapshot and recorded method; explicit recalculation creates a new context |
| Delete result | Delete its snapshot through existing result ownership; collect unused contexts on a safe save |
| Accepted new result while continuous processing is enabled | Queue after the result update; show pending until calculation commits |
| Input changes while its calculation is queued/running | Supersede old work, discard its late output, and queue the newest eligible revision |
| Result imported from Android without the desktop extension | Show not calculated or reconcile against the retained desktop snapshot using complete semantic validation |

Canonical digests must exclude names, timestamps unrelated to route selection, encryption ciphertext/salts, file paths, and database-specific UUID rewrites. Preserve or remap context references across imports. Compare canonical route/code/role semantics, and maintain a course revision token that can be checked while geometry is locked. Unknown analysis versions or broken context links are unavailable for current export.

Gate: a mutation matrix proves desktop invalidation and preservation, including edits during execution. No stale value is returned by the desktop accessor, and routine scoring does not continually invalidate unchanged routes. Android requires no new invalidation logic because it has no supported analysis storage or output.

## Stage 5 — Background batch, continuous queue, and safe saving

Implement a headless desktop service first, with an injected frozen elevation provider and cancellation/progress callbacks. Expose it through the existing automation CLI with a thin Justfile recipe for repeatable tests, then add a compact Results action: `Calculate Classic Route Lengths…`. The launch dialog selects Classic races/categories and either `Process existing results` or `Process existing and new downloads`. Starting the latter explicitly enables continuous processing for that desktop session.

Workflow: select scope/mode → preflight reference and coverage → start background work → commit validated completions → notify when the requested results and export projection are ready. Establish or accept reference changes before launch. Routine completed calculations need no modal review/save confirmation. Run work on a bounded desktop worker, initially one calculation worker, and perform only short serialized model updates on the app/session owner. Keep it independent of the visible Results panel so switching tabs does not stop it. Background means while the app is running; no operating-system daemon is in scope.

Hook queue notifications after `appendSportIdentDownload` / the committed `DesktopProjectSession` result update, including single and continuous download modes, duplicate replacement, manual edits, and imports. Use the actual routed race and result identity from series routing, not whichever event happens to be visible when work finishes. Do not open a second serial connection or put elevation work on the serial reader, card acknowledgement, scoring, or printing path. Results downloaded only on Android become eligible when imported into the desktop; no new device synchronization is implied.

Represent queue entries by event, result, semantic input digest, and frozen course-context revision. Coalesce duplicate notifications, supersede replaced results, and check these identities before accepting output. Bound active sampling memory and queued work; overflow can set a needs-rescan marker and rescan current results rather than losing work or retaining unlimited snapshots. A result/course edit may invalidate that result while other jobs continue. Reference changes pause the affected course until a new compatible context is prepared; never silently switch terrain sources mid-event.

Queue observation compares result-input digests, so writing analysis metadata, refreshing views, or changing a job state cannot enqueue the same result again. Retain unlocked calculation inputs only for the active session/context and release them when it closes; recovery checkpoints must not store passwords or newly exposed protected geometry.

Deduplicate identical semantic course/order contexts and cache directed sampled legs. Cache keys include coordinates, endpoint fallback-relevant data, method, and elevation-context identity; SI codes alone are insufficient. Join cached samples in each competitor's actual order and run complete-route metrics once per unique route. Bound cache memory and check cancellation while sampling and between routes.

Commit completed results incrementally in small coalesced batches. Pause stops new work; cancel discards unfinished work and retains already accepted completions. Missing-location/coverage failures become per-result `unavailable` states, with actionable explanations; do not retry them continuously without an input/context change or explicit retry. On restart, rebuild outstanding work from native results and snapshot digests after the user resumes; do not serialize threads or partially processed elevation samples. Closing/unloading the target event cancels or pauses its worker and prevents late writes to a newly opened event; switching the visible member within an owned series may continue processing the retained series context.

Persistence needs two explicit boundaries because the current desktop download handler can leave the event dirty in memory. Merge completed metadata into the latest session model without replacing result records. Write a coalesced, atomic desktop recovery checkpoint containing analysis metadata and the exact input/context digests; do not persist protected geometry in plaintext or pretend this checkpoint saves otherwise-unsaved readouts. Embed/attach the metadata when the normal event save occurs. If the event is already fully saved and its disk revision matches, the service can save analysis-only changes through the existing session owner. Never autosave unrelated user edits just because a calculation finished. The UI distinguishes `ready for viewing/export` from `saved with event`, and retains the existing unsaved-event indication.

Serialize all background metadata saves with user saves and series/readout routing. Recheck result/context digests and the on-disk archive digest immediately before saving; unrelated edits should be merged or deferred, not overwritten or allowed to discard useful completed work. For `.roseries`, combine each pending save batch into one `replaceArchive` call, preserving its conflict detection and atomic replacement. Debounce writes so a burst of downloads does not rewrite the entire archive per result. Checkpoint recovery accepts only snapshots whose persisted native inputs still match. Test crash/error boundaries, including disk replacement succeeding but workspace materialization failing. Multiple standalone files have separate atomic saves and reported outcomes, not a cross-file transaction.

The current standalone `DesktopProjectFiles.write` uses `Files.writeString`, so atomic standalone persistence is not already guaranteed. Before enabling automatic analysis-only native saves, add a narrowly scoped temporary-file-and-replace path with conflict checks, or defer native writes to the ordinary save workflow and rely on the atomic analysis checkpoint. Include this in the persistence gate rather than assuming the series writer's guarantees apply to standalone files.

Notifications: show one persistent progress/status area with current, pending, unavailable, and stale counts. A one-shot batch reports completion after its launch watermark has been processed, the validated export projection has updated, and the recovery checkpoint has succeeded. Continuous mode reports `Caught up; watching for new results` when it drains, with debounced/coalesced notifications rather than a toast per card. Report failures and save deferrals accurately. New work arriving after a completion watermark does not invalidate that completion claim. Use in-app notifications first; operating-system notifications are optional and must not be required for correctness.

Gate: burst downloads, duplicate replacement, course edits, race switching, cancellation, restart, and disk failures cannot attach an obsolete metric or overwrite later edits. The UI and serial download path remain responsive. Ready notifications agree with the actual export projection and persistence status.

## Stage 6 — Desktop result views and export threading

Project completed snapshots through the desktop validity/accessor API. Desktop result views observe updates immediately, including during a race, and show pending/stale/unavailable states distinctly. Exports format the current validated projection; they do not prompt for passwords or perform terrain analysis inline. Display `Estimated effective route length`, with integer meters and detailed comparison states in machine-oriented output, and the two-decimal kilometer wording specified in the operational notes for human-readable results. Category headings show the certified reference order and EL. Treat absence as blank/omitted, never zero.

An export captures an immutable result/analysis revision so it cannot mix edits or completions across rows. If work is pending, let the user export currently available values with a coverage notice, or wait asynchronously for the results present at that export request to finish. Later downloads do not extend that watermark indefinitely. The post-race workflow can process pending results, save the event, then export; unavailable cases stay explicit. `Export data ready` means desktop data can be exported, not that files have been written or a remote website republished. Export-to-file and remote publication remain existing user-requested actions.

If a captured result/course is edited or deleted while an export waits, supersede that pending export with an explicit refresh-required status. Do not wait forever for an obsolete revision whose worker output was correctly discarded. Once its requested inputs are complete, capture their analysis projection and serialize the export from that consistent snapshot.

Use focused tests after each stage. Run the broader shared and desktop gates once the integrated feature is complete, through current Justfile wrappers with Temurin 17 and serialized Gradle execution. Acceptance evidence:

1. Ideal-order fixtures produce exactly the saved ideal length; near-rounding values also match.
2. Changed orders agree with an independent whole-route test oracle; junction smoothing and source gaps are exercised. Exhaustively enumerated small Classic courses produce no shorter complete legal order than their certified reference, allowing ties.
3. Provenance mismatches and unsupported geometry fail explicitly. Legacy reference adoption shows changes before saving and never overstates historical provenance.
4. Desktop native save/reopen/copy and recovery preserve snapshots and context identity; Android core event imports and legacy exports remain unchanged. Android round trips may omit desktop analysis and cannot revive stale metadata on return.
5. Mixed-series tests calculate Classic members only and preserve all non-Classic data semantically.
6. Golden outputs cover no metrics, queued/calculating states, current metrics, missing metrics, stale metrics, different-control-set results, and exporting while work is pending; report/PDF/public-site layouts are inspected. Android shared-default fixtures never gain metric output.
7. Benchmark cold-cache loading, warm repeated routes, hashing, calculation, and saving separately on anonymized representative fixtures. Track unique directed-leg lookups to verify reuse. Establish measured latency/memory bounds before release instead of promising a duration now.
8. On a copy of real Classic data, review exact ideal matches, alternate orders, unresolved controls, and shorter-than-reference anomalies. Verify the saved file by fresh decode and exports after restarting without the elevation cache available. Keep original user archives untouched.
