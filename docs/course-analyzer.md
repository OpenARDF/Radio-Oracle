# Course Analyzer

The Course Analyzer evaluates protected radio-orienteering course data after controls and route geometry have been imported for a category. It uses the course-design definitions from `Radio Orienteering Courses: Design and Set Guidelines, Rev 23-Mar-2024`, and checks course requirements from `USA Rules for Radio Orienteering, Effective Date: 1 Jan 2026`. The analyzer report names the rules document once in the report header.

## Definitions

- Stored route: the ideal route order saved for the category, resolved against the category's assigned controls.
- Calculated ideal route: an independent route candidate generated from the start, finish, assigned foxes, beacon, and spectator if the category uses one.
- Horizontal distance: straight-line distance between route points, without elevation penalty.
- Route length: the imported route geometry length when a stored route exists; for calculated candidates, the straight-line distance through the calculated point order.
- Climb: positive elevation gain along the route.
- Effective length: route length plus ten times climb. For example, 5.00 km with 100 m of climb is 6.00 km effective length.

The analyzer report displays length values in kilometers to hundredths (`x.xx km`). Climb is displayed in meters with no decimal places. Analyzer time values omit a zero hours field, so `00:58:50` is displayed as `58:50`.

## Elevation Handling

When local Elevation Cache samples are complete for the relevant route or course points, the analyzer uses effective length as the primary comparison metric. If elevations are missing or incomplete, analysis still runs and falls back to horizontal distance. The report explains which metric was used in each section.

For the calculated ideal route, Radio-Oracle has no imported track line, so it samples each calculated straight leg at short intervals and applies cached elevation values to those samples. That sampled geometry is used for the calculated route's profile, climb, effective length, route comparison, and movement timing. If a cache value is unavailable for an intermediate sample, endpoint elevation interpolation is used when possible. When calculated-route samples are not covered by the local Elevation Cache, the incomplete-data warning states that the calculated route did not use downloaded elevations along the route and offers a `Download Calculated Route Elevations` action to create a 10 m USGS 3DEP cache around the calculated route bounds.

The Elevation Cache resolution setting is the spacing of Radio-Oracle's local sampling grid. For example, entering `3` meters creates an approximately 3-meter cache grid over the selected bounds. It does not guarantee that the upstream USGS source DEM is 3-meter data at every sampled point. Radio-Oracle samples the USGS 3DEP dynamic elevation service, which is based on multi-resolution DEM sources. USGS documents 1/9 arc-second, approximately 3-meter, DEM coverage as partial in the conterminous United States, while 1/3 arc-second, approximately 10-meter north/south, DEM coverage is the full-coverage seamless U.S. product. As a result, a 3-meter cache may contain closely spaced samples derived from coarser source data where 3-meter or better DEM coverage is not available.

Relevant USGS references:

- 3DEP products and services: https://www.usgs.gov/3d-elevation-program/about-3dep-products-services
- USGS DEM resolution FAQ: https://www.usgs.gov/faqs/what-projection-horizontal-datum-vertical-datum-and-resolution-a-usgs-digital-elevation-model
- USGS 3DEP dynamic elevation service: https://elevation.nationalmap.gov/arcgis/rest/services/3DEPElevation/ImageServer

## Speed Model

Estimated times use an elite-competitor baseline pace by race format: 4:38 min/km for Classic-style courses (3.6 m/s), 3:58 min/km for Sprint (4.2 m/s), and 4:54 min/km for Foxoring (3.4 m/s). The analyzer then applies a built-in provisional age/gender category multiplier and the event-wide Course Analyzer speed factor. The category multipliers are not rules-derived or event-calibrated yet; they are separated into a named speed-factor table so future map-aware route modeling can combine category assumptions with per-leg course-condition factors.

When elevation is available, movement time is based on effective length for each leg: horizontal length plus ten times positive climb. This same effective-length movement model is used for the stored route in Section 1 and for the calculated point-to-point route in Section 2. If elevation is incomplete, movement time falls back to horizontal distance. The current model does not include accumulated fatigue across the course.

For Classic-style fox controls, the timing model distinguishes arrival near the fox from departure after punching. If the competitor arrives while the fox is off the air, the analyzer assumes the competitor waits until that fox begins transmitting. It then adds a fixed 30 seconds to find and punch the fox before the competitor starts the next leg. If the competitor arrives while the fox is already transmitting, the same 30-second find-and-punch allowance is added from the arrival time.

## Report Sections

Section 1 appears only when a stored ideal route is available. It analyzes the saved route order, imported route geometry, leg lengths, estimated splits, climb, effective length when available, and Classic wait times. Classic leg splits and cumulative times include any fox wait plus the 30-second find-and-punch allowance before the competitor departs for the next leg. Timing breakdown rows separate movement time, fox wait time, and find/punch allowance. Leg rows show the wait at the destination fox in parentheses after the cumulative time.

Section 1 also checks the stored route against the applicable USA rules. Classic and Foxoring checks compare the route's effective length, or horizontal fallback when elevation is incomplete, with the category length range and compare assigned fox count with the category requirement. Sprint checks compare assigned fox count with twice the Classic category assignment and compare estimated ideal time with the approximately 15-minute target. Spacing checks use straight-line distance between known protected point coordinates: Classic foxes and the finish beacon must be outside the start exclusion zone, at least 400 m from the finish beacon, and at least 400 m from other foxes; Youth Classic uses the 500 m start exclusion zone from Appendix Y. Sprint checks the 100 m transmitter spacing and the 100 m fox start exclusion zone, while allowing the beacon and spectator to be less than 100 m from the start. Foxoring checks the 250 m transmitter spacing and 250 m start exclusion zone. Minimum spacing rows check all applicable points or transmitter pairs, then report the nearest transmitter to the start or closest transmitter pair as the limiting result. Rule-check rows put the measured result first and the applicable rule in parentheses. Failed rule checks are shown as red violation text.

Category names are matched to the USA rules tables by normalized category code, so names such as `M-21` or `M 21` are evaluated using the `M21` rules. When the stored category name differs from the table code, the report includes a warning noting the discrepancy and the rules key used.

Section 1 also includes a separate wait-time analysis for Classic-style courses. It estimates arrival phase at each fox on the stored route and checks whether renumbering fox transmit slots could reduce total waiting. Candidate renumberings are evaluated by replaying the full route timing, so a wait at one fox changes the estimated arrival phase at later foxes. The report shows current wait, best wait, and the likely improvement. These wait estimates depend on the route and speed model. The model applies a race-format baseline speed, a category age/gender multiplier, and the event-wide Course Analyzer speed factor, but it still does not know map passability or fatigue; barriers, slow terrain, unusual weather, and competitor profile can shift real arrival times.

Section 2 always attempts to calculate an independent ideal route when enough course points are available. For Classic-style courses, the analyzer exhaustively permutes assigned fox locations and any spectator point, keeps the beacon last before the finish, then selects the shortest candidate by effective length when elevations are complete or by horizontal distance otherwise. Sprint routes are calculated as two separate loops: start through the slow foxes to the spectator, then spectator through the fast foxes to the beacon and finish, with each loop capped at 120 permutations. Foxoring routes with six or fewer foxes are calculated exhaustively. Larger Foxoring routes use the hybrid heuristic described below. The calculated elevation profile is drawn from the sampled straight-leg geometry and marks fox locations with dots for comparison against the stored-route profile. For Classic-style courses, fox assignments are optimized for the calculated route to minimize wait time using the same wait-and-departure timing model. Section 2 shows the calculated physical route once with the stored fox numbering and then immediately with the calculated fox numbering; leg analysis, optimized wait rows, summary labels, elevation-profile markers, 2D depictions, PDF graphics, and KML exports use the calculated numbering. Because Section 2 can change fox assignments, a large ideal-time difference may come from reduced fox waiting rather than from route length alone; use the timing breakdown and wait rows to compare the cause.

## Foxoring Route Heuristic

Foxoring courses commonly have ten foxes and can have up to twelve. Exhaustively checking every route order is not practical at that size: ten foxes would require 3,628,800 route orders and twelve foxes would require 479,001,600 route orders before elevation sampling and rule reporting are considered. Radio-Oracle therefore uses exhaustive search only through six foxes. Above six foxes, it calculates two non-exhaustive candidates and keeps the shorter one.

The first candidate is a nearest-neighbor route followed by a 2-opt cleanup. The analyzer starts at Start, repeatedly adds the nearest unvisited fox, then repeatedly checks whether reversing any section of the route shortens the total route. This candidate is fast and is good at removing obvious crossings or backtracking, but it can miss improvements that require moving a fox to a very different part of the order.

The second candidate is a rolling five-fox exhaustive-window route followed by a full-route 2-opt cleanup. The first five-fox window prefers foxes closest to Start that are not closer to Finish than to Start; this helps keep finish-side foxes from being pulled into the beginning of the route. If fewer than five foxes meet that condition, the window is filled with the remaining nearest foxes so the local search still has five controls when possible. The analyzer exhaustively optimizes that five-fox window toward the route terminal point, normally the beacon. It then commits the first fox from the best local order, slides the remaining four foxes forward, adds the nearest remaining fox to the end of the window, and optimizes the new five-fox window. This repeats until all foxes have entered the route. Finally, a full-route 2-opt pass is applied so the complete route can still remove larger crossings or backtracking introduced by earlier window decisions.

For both Foxoring candidates, the beacon is treated as a fixed terminal control after all foxes and before Finish. It is not permuted as one of the foxes. Candidate comparison uses effective length when all sampled route points have elevation data; if elevation is incomplete, comparison falls back to horizontal straight-line length. The selected route is still an advisory candidate because the app does not currently know map passability, vegetation, water barriers, out-of-bounds areas, or other terrain constraints.

If the calculated ideal route uses the same fox locations in the same order as the stored route, Section 2 is collapsed to a short match result instead of repeating leg, wait, profile, and map details that are already covered by Section 1. In that case Section 3 says that the stored and calculated routes match and reports the stored-route summary values without repeating separate calculated-route detail rows. The graphics and KML export include only the stored route depiction/profile, and `Apply Calculated Route` is disabled because there is no different calculated route to apply.

Section 3 summarizes the results. When both a stored route and calculated candidate exist, it compares their order, distance metrics, estimated time, wait behavior, USA rules checks, elevation profiles, and compact 2D route depictions. The summary effective-length row repeats the applicable Classic or Foxoring category length range when that rule exists. The summary climb-percent row shows the calculated route climb ratio when available, otherwise the stored route climb ratio, with the Classic-style 6% climb limit in parentheses. When no stored route exists, it summarizes only the calculated candidate.

The `Export Analysis...` button writes the PDF report and a companion KML file with the same filename stem. The KML contains selectable folders for the stored foxes and route when a stored route is present, and for the calculated foxes and route. The calculated folder applies any improved Classic fox-numbering assignments recommended by the wait-time optimization.

The `Apply Calculated Route` button applies the calculated ideal route to the open Event File. It replaces the selected category's protected ideal order and re-encrypts the protected course data with that ideal order. It does not change the global Setup > Controls SI-code-to-public-label mapping, and it does not change downloaded SI punch records. Category assignments continue to identify physical controls by control ID, so competitors remain assigned to the same stored controls unless the route application explicitly replaces the selected category's stored route/order data. The change is saved in memory as an unsaved Event File change; save the Event File to persist it to disk.

The `Apply Fox Renumbering Only` button applies only the Section 1 wait-time renumbering recommendation when it improves the stored route's Classic wait estimate. It re-encrypts affected protected course labels and protected ideal-order text across categories, without replacing stored route geometry and without changing the definitive Setup > Controls public labels or downloaded SI punch records. The button is disabled when no improved renumbering was calculated.

Setup > Controls remains the definitive SI-code-to-public-label mapping. When a stored control is edited there, derived category control-point copies are refreshed so category assignments stay consistent with the edited control definition. Downloaded SI card punch codes are not rewritten; result displays and exports should resolve labels from the current Controls table wherever a punched SI code still matches a stored control.

The password-locked protected course screen also includes an `Update Location` tool for control coordinate corrections. Control coordinates are protected data: they are shown only after the unlock key has been applied, and location edits update encrypted protected course payloads rather than public Event File control fields. If legacy public latitude/longitude values are encountered during a protected location update, they are cleared. Because changing a control location makes any previously stored imported route geometry and route-derived length/climb values suspect, affected protected course payloads have stored route geometry, route length, climb, and route sample count cleared. Run Course Analyzer again after the location update to calculate the new ideal route, ideal time, fox numbering, route length, and related comparisons.

KML/KMZ point placemarks and GPX waypoints can also update protected control locations during protected controls/route import. The importer matches point or waypoint names to existing controls by SI code, control label, or public label, compares their latitude/longitude against encrypted protected coordinates, and applies only changed locations. GPX route (`rte`) and track (`trk`) names are matched to Event File category names, and route or track points provide the stored route geometry. If a route object has no category indication, a single route is assumed to be `M21`; multiple unnamed route objects are assigned through existing older male categories first, then female categories, with missing fallback categories offered for creation. The import review warns about every category assumption before the data is kept. OCAD-specific GPX import/export conventions were not found in public documentation during implementation, so the current GPX support uses standard GPX 1.1 waypoints, routes, tracks, WGS84 latitude/longitude, and meter elevations as placeholders. Controls CSV import does not contain latitude/longitude fields, so it cannot update protected control locations.

## Algorithm Limits

Classic calculated-route search is exhaustive and currently limited to eight permuted course points. Sprint calculated-route search is exhaustive separately for the first and fast loops, with each loop capped at 120 permutations. Foxoring calculated-route search is exhaustive through six foxes; above six foxes, the analyzer uses the non-exhaustive hybrid search described above and states in the report that the Foxoring candidate was non-exhaustive.

The analyzer does not currently import map passability or symbol constraints. It does not know about out-of-bounds areas, dense vegetation, lakes, uncrossable creeks and rivers, cliffs, fences, walls, or other barriers and impediments to on-foot navigation. This limits both ideal-route selection and Classic wait-time estimates, because the true best route and actual arrival phases can differ from straight-line or imported-route geometry when terrain forces detours or slows travel. Future map-aware timing should preserve the category speed-factor table as one input and apply additional per-leg speed factors for vegetation, runnability, elevation change, barriers, and other mapped conditions.
