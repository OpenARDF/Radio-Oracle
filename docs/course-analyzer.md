# Course Analyzer

The Course Analyzer evaluates protected radio-orienteering course data after controls and route geometry have been imported for a category. It uses the course-design definitions from `Radio Orienteering Courses: Design and Set Guidelines, Rev 23-Mar-2024`, and checks course requirements from `USA Rules for Radio Orienteering, Effective Date: 1 Jan 2026`. The analyzer report names the rules document once in the report header.

## Definitions

- Saved route: the route/order currently available to Analyzer in the candidate design. When a draft exists, this is draft data; race downloads and result exports continue to use the applied course.
- Imported data: route/control data read from a KML/KMZ or GPX file into a persisted course draft. Choosing `Analyze Imported Data` makes it available to Analyzer. `Save Race` preserves the draft and the applied courses separately; it does not apply the draft.
- Ideal route: the property of a course defined by the route from start to finish, through each required control point, that has the shortest effective length. It is determined by the start, finish, control locations, and elevation contours between those points; it is not a matter of course-setter preference.
- Calculated ideal route: Radio-Oracle's determination of the ideal route from the start, finish, assigned foxes, beacon, and spectator if the category uses one. When the route search is exhaustive, the shortest route by effective length is by definition the ideal route for the course, subject only to map data such as barriers, out-of-bounds areas, or other navigation constraints that Radio-Oracle does not currently model.
- Horizontal distance: straight-line distance between route points, without elevation penalty.
- Route length: the saved route geometry length when a saved route exists; for calculated routes, the straight-line distance through the calculated point order.
- Climb: positive elevation gain along the route after elevation-profile smoothing and small-noise filtering.
- Effective length: route length plus ten times climb. For example, 5.00 km with 100 m of climb is 6.00 km effective length.

The analyzer report displays length values in kilometers to hundredths (`x.xx km`). Climb is displayed in meters with no decimal places. Analyzer time values omit a zero hours field, so `00:58:50` is displayed as `58:50`.

Before entering Course Analyzer, Radio-Oracle requires the Race File model to be clean. If other Race File edits are pending, the user must cancel entry, save and continue, or dump the pending edits by reloading the Race File from disk before analyzer imports or calculated-route saves can be made active.

## Elevation Handling

When local Elevation Cache samples are complete for the relevant route or course points, the analyzer uses effective length as the primary comparison metric. If elevations are missing or incomplete, analysis still runs and falls back to horizontal distance. The report explains which metric was used in each section.

For the calculated ideal route, Radio-Oracle has no imported track line, so it samples each calculated straight leg at short intervals and applies cached elevation values to those samples. That sampled geometry is used for the calculated route's profile, climb, effective length, route comparison, and movement timing. If a cache value is unavailable for an intermediate sample, endpoint elevation interpolation is used when possible. When calculated-route samples are not covered by the local Elevation Cache, the incomplete-data warning states that the calculated route did not use downloaded elevations along the route and offers a `Download Calculated Route Elevations` action to create a 10 m USGS 3DEP cache around the calculated route bounds.

Climb is calculated from the sampled elevation profile with the same shared route-metric logic for saved routes, imported KML/GPX routes, calculated routes, and generated-course comparisons. Radio-Oracle applies a 50 m distance-based median smoothing window, then counts sustained ascents using a 2 m prominence threshold. This avoids adding every small LiDAR or raster interpolation wiggle as extra climb while still counting gradual uphill sections whose individual sample-to-sample changes are small.

The Elevation Cache resolution setting is the spacing of Radio-Oracle's local sampling grid. For example, entering `3` meters creates an approximately 3-meter cache grid over the selected bounds. It does not guarantee that the upstream USGS source DEM is 3-meter data at every sampled point. Radio-Oracle samples the USGS 3DEP dynamic elevation service, which is based on multi-resolution DEM sources. USGS documents 1/9 arc-second, approximately 3-meter, DEM coverage as partial in the conterminous United States, while 1/3 arc-second, approximately 10-meter north/south, DEM coverage is the full-coverage seamless U.S. product. As a result, a 3-meter cache may contain closely spaced samples derived from coarser source data where 3-meter or better DEM coverage is not available.

For local LAS/LAZ point-cloud imports, Radio-Oracle rasterizes the point cloud through PDAL, classifies ground with SMRF, keeps ground-classified points, then samples the resulting raster with GDAL. Elevation-cache point lookup uses weighted bilinear interpolation when all four neighboring grid values are available, with an average-of-available-neighbors fallback at sparse or edge cells.

Relevant USGS references:

- 3DEP products and services: https://www.usgs.gov/3d-elevation-program/about-3dep-products-services
- USGS DEM resolution FAQ: https://www.usgs.gov/faqs/what-projection-horizontal-datum-vertical-datum-and-resolution-a-usgs-digital-elevation-model
- USGS 3DEP dynamic elevation service: https://elevation.nationalmap.gov/arcgis/rest/services/3DEPElevation/ImageServer

## Speed Model

Estimated times use an elite-competitor baseline pace by race format: 4:38 min/km for Classic-style courses (3.6 m/s), 3:58 min/km for Sprint (4.2 m/s), and 4:54 min/km for Foxoring (3.4 m/s). The analyzer then applies a built-in provisional age/gender category multiplier and the race-wide Course Analyzer speed factor. The category multipliers are not rules-derived or race-calibrated yet; they are separated into a named speed-factor table so future map-aware route modeling can combine category assumptions with per-leg course-condition factors.

Imported KML/KMZ course files may specify per-leg speed factors in placemark descriptions using `SS=#.##`, where the value is from `0.01` through `4.99`. `SS` can be placed on the Start placemark, a fox, beacon, spectator, or route LineString placemark. A valid `SS` value replaces the race-wide Course Analyzer speed factor for the leg immediately after that course object. If no `SS` is present, the leg uses the race-wide speed factor. `SS` on the Finish placemark is ignored. If both the route LineString and the Start placemark specify `SS`, the Start value is used for the first leg.

When elevation is available, movement time is based on effective length for each leg: horizontal length plus ten times positive climb. This same effective-length movement model is used for the saved route in Section 1 and for the calculated point-to-point route in Section 2. If elevation is incomplete, movement time falls back to horizontal distance. Fatigue is not a factor in deciding the ideal route. It can affect ideal time, but the current estimated-time model does not yet apply a separate accumulated-fatigue adjustment.

For Classic-style fox controls, the timing model distinguishes arrival near the fox from departure after punching. If the competitor arrives while the fox is off the air, the analyzer assumes the competitor waits until that fox begins transmitting. It then adds a fixed 30 seconds to find and punch the fox before the competitor starts the next leg. If the competitor arrives while the fox is already transmitting, the analyzer assumes the competitor runs straight to the fox and punches without extra delay.

## Report Sections

Section 1 appears only when a saved route is available. It analyzes the saved route order, saved route geometry, leg lengths, estimated splits, climb, effective length when available, and Classic wait times. Classic leg splits and cumulative times include any fox wait plus the 30-second find-and-punch allowance only when waiting was required before the competitor departs for the next leg. Timing breakdown rows separate movement time, fox wait time, and find/punch allowance. Leg rows show the wait at the destination fox in parentheses after the cumulative time.

Section 1 also checks the saved route against the applicable USA rules. Classic and Foxoring checks compare the route's effective length, or horizontal fallback when elevation is incomplete, with the category length range and compare assigned fox count with the category requirement. Sprint checks compare assigned fox count with twice the Classic category assignment and compare estimated ideal time with the approximately 15-minute target. Spacing checks use straight-line distance between known protected point coordinates: Classic foxes and the finish beacon must be outside the start exclusion zone, at least 400 m from the finish beacon, and at least 400 m from other foxes; Youth Classic uses the 500 m start exclusion zone from Appendix Y. Sprint checks the 100 m transmitter spacing and the 100 m fox start exclusion zone, while allowing the beacon and spectator to be less than 100 m from the start. Foxoring checks the 250 m transmitter spacing and 250 m start exclusion zone. Minimum spacing rows check all applicable points or transmitter pairs, then report the nearest transmitter to the start or closest transmitter pair as the limiting result. Rule-check rows put the measured result first and the applicable rule in parentheses. Failed rule checks are shown as red violation text.

Category names are matched to the USA rules tables by normalized category code, so names such as `M-21` or `M 21` are evaluated using the `M21` rules. When the stored category name differs from the table code, the report includes a warning noting the discrepancy and the rules key used.

Section 1 also includes a separate wait-time analysis for Classic-style courses. It estimates arrival phase at each fox on the saved route and checks whether renumbering fox transmit slots could reduce total waiting. Candidate renumberings are evaluated by replaying the full route timing, so a wait at one fox changes the estimated arrival phase at later foxes. The report shows current wait, best wait, and the likely improvement. These wait estimates depend on the route and speed model. The model applies a race-format baseline speed, a category age/gender multiplier, the race-wide Course Analyzer speed factor, and any imported KML/KMZ `SS` per-leg overrides, but it still does not know map passability and does not yet apply a separate accumulated-fatigue adjustment; barriers, slow terrain, unusual weather, fatigue, and competitor profile can shift real arrival times.

Section 2 always attempts to determine the ideal route when enough course points are available. For Classic-style courses, the analyzer exhaustively permutes assigned fox locations and any spectator point, keeps the beacon last before the finish, and compares every route order by effective length when elevations are complete or by horizontal distance otherwise. With five permuted foxes, this means all 120 route permutations are examined. The route with the shortest effective length is by definition the ideal route for the course; a saved route that is longer is not ideal even if it was previously supplied as the expected route. Sprint routes are calculated as two separate loops: start through the slow foxes to the spectator, then spectator through the fast foxes to the beacon and finish, with each loop capped at 120 permutations. Foxoring routes with six or fewer foxes are calculated exhaustively. Larger Foxoring routes use the hybrid heuristic described below and are reported as non-exhaustive candidates rather than definitive ideal routes. The calculated elevation profile is drawn from the sampled straight-leg geometry and marks fox locations with dots for comparison against the saved-route profile. The 2D route depictions use the bundled WMM2025 model to calculate magnetic declination for the course center and rotate the depiction so magnetic north is up. NOAA/NCEI lists WMM2025 as expiring on December 31, 2029; after that date, Radio-Oracle continues using the expired coefficients for magnetic-north route depictions and shows a warning in the analyzer/report output until the app is updated with a newer WMM model. For Classic-style courses, fox assignments are optimized for the calculated route to minimize wait time using the same wait-and-departure timing model. Section 2 shows the calculated physical route once with the saved fox numbering and then immediately with the calculated fox numbering; leg analysis, optimized wait rows, summary labels, elevation-profile markers, 2D depictions, PDF graphics, and KML exports use the calculated numbering. Because Section 2 can change fox assignments, a large ideal-time difference may come from reduced fox waiting rather than from route length alone; use the timing breakdown and wait rows to compare the cause.

## Foxoring Route Heuristic

Foxoring courses commonly have ten foxes and can have up to twelve. Exhaustively checking every route order is not practical at that size: ten foxes would require 3,628,800 route orders and twelve foxes would require 479,001,600 route orders before elevation sampling and rule reporting are considered. Radio-Oracle therefore uses exhaustive search only through six foxes. Above six foxes, it calculates two non-exhaustive candidates and keeps the shorter one.

The first candidate is a nearest-neighbor route followed by a 2-opt cleanup. The analyzer starts at Start, repeatedly adds the nearest unvisited fox, then repeatedly checks whether reversing any section of the route shortens the total route. This candidate is fast and is good at removing obvious crossings or backtracking, but it can miss improvements that require moving a fox to a very different part of the order.

The second candidate is a rolling five-fox exhaustive-window route followed by a full-route 2-opt cleanup. The first five-fox window prefers foxes closest to Start that are not closer to Finish than to Start; this helps keep finish-side foxes from being pulled into the beginning of the route. If fewer than five foxes meet that condition, the window is filled with the remaining nearest foxes so the local search still has five controls when possible. The analyzer exhaustively optimizes that five-fox window toward the route terminal point, normally the beacon. It then commits the first fox from the best local order, slides the remaining four foxes forward, adds the nearest remaining fox to the end of the window, and optimizes the new five-fox window. This repeats until all foxes have entered the route. Finally, a full-route 2-opt pass is applied so the complete route can still remove larger crossings or backtracking introduced by earlier window decisions.

For both larger Foxoring candidates, the beacon is treated as a fixed terminal control after all foxes and before Finish. It is not permuted as one of the foxes. Candidate comparison uses effective length when all sampled route points have elevation data; if elevation is incomplete, comparison falls back to horizontal straight-line length. The selected route is an advisory candidate, not a definitive ideal route, because the search is non-exhaustive and the app does not currently know map passability, vegetation, water barriers, out-of-bounds areas, or other terrain constraints.

If the calculated ideal route uses the same fox locations in the same order as the saved route, Section 2 is collapsed to a short match result instead of repeating leg, wait, profile, and map details that are already covered by Section 1. In that case Section 3 says that the saved and calculated routes match and reports the saved-route summary values without repeating separate calculated-route detail rows. The graphics and KML export include only the saved route depiction/profile, and the report avoids duplicating that route. `Review and Apply Courses` remains available to validate and apply the complete race design, including an imported route that already matches the calculated route.

Section 3 summarizes the results in separate Saved and Calculated groups with a visual divider between them. The Saved group keeps the saved route, saved-route distance metrics, estimated time, and saved-route wait/renumbering information together. The Calculated group keeps the calculated route order, distance metrics, estimated time, and optimized wait information together. Section 3 then adds a Course Recommendation paragraph that states how Radio-Oracle recommends saving the analysis if map information or other outside data do not change the result. When the saved route is longer than the ideal route, the recommendation states how much longer it is, gives the calculated ideal route length that should be used as the course's effective length for the category, and identifies the ideal route order with calculated fox numbering. If that calculated route falls outside the category rules length range, or if the saved and calculated ideal routes match and therefore share an out-of-range length, the recommendation adds a caveat: the calculated route should still be used as the honest representation of the course's overall difficulty and length, but the better course-design action is to redesign the course by moving the start, finish, or foxes until the calculated ideal route length falls inside the rules range. If the saved and calculated physical routes match but wait-time renumbering improves the model, the recommendation is to save fox renumbering only. If waits exceed 30 seconds under current fox numbering, the recommendation calls out the suggested renumbering. If waits still exceed 30 seconds under the calculated or best-case fox numbering, the recommendation suggests exploring course modifications, such as moving foxes, to reduce wait time at the affected foxes. If neither calculated-route nor renumbering improvement is available, the recommendation is to keep the saved data as is. Goodness metrics retain the rule-facing comparisons, including effective-length range checks and climb-percent limits, and are grouped as shared, Saved, and Calculated metrics. Saved and Calculated Goodness metric subsections use corresponding row entries, including separate shortest-possible-route checks for each route. When no saved route exists, Section 3 summarizes only the calculated route.

The `Export Analysis...` button writes the PDF report and a companion KML file with the same filename stem. The KML contains selectable folders for the saved foxes and route when a saved route is present, and for the calculated foxes and route. The calculated folder applies any improved Classic fox-numbering assignments recommended by the wait-time optimization.

The `Review and Apply Courses` button opens a review for all courses in this race, including inactive imported mappings. Confirm each placement's physical SI station; coordinates are shown to distinguish locations. `Prepare all courses` freezes the accepted numbering and calculates the other categories using their own required controls. It validates complete geometry, order, metrics, station assignments, roles and course coverage before offering `Apply reviewed courses`.

Apply updates the Controls labels, category assignments, protected geometry, ideal orders and metrics together, preserving station codes and original downloaded punches. Save Race writes the result to disk. A late calculation cannot replace a newer draft. Reapplying identical content preserves the saved design, including existing encrypted payloads.

`Save Draft Numbering` retains the Section 1 numbering proposal within the candidate design. It does not apply the race courses. Continue analysis or export a draft report/KML, then use the same review and Apply operation when ready. `Discard course draft` restores the applied design; Save Race persists that cancellation.

Apply is blocked after recorded activity begins. The review offers `Export revised race copy…`, which creates a new race without readouts, results, publication links or drawn starts, while retaining registrations and the candidate design. Open that new file to continue. The historical race remains available with its recorded assignments and punches.

Setup > Controls remains the definitive SI-code-to-public-label mapping. When a stored control is edited there, derived category control-point copies are refreshed so category assignments stay consistent with the edited control definition. Downloaded SI card punch codes are not rewritten; result displays and exports should resolve labels from the current Controls table wherever a punched SI code still matches a stored control.

The password-locked protected course screen also includes an `Update Location` tool for control coordinate corrections. Control coordinates are protected data: they are shown only after the unlock key has been applied, and location edits update the candidate draft's protected payloads. The applied race is unchanged until review and Apply. If legacy public latitude/longitude values are encountered during a protected location update, they are cleared. Because changing a control location makes any previously imported route geometry and route-derived length/climb values suspect, affected protected course payloads have imported route geometry, route length, climb, and route sample count cleared. Run Course Analyzer again after the location update to calculate the new ideal route, ideal time, fox numbering, route length, and related comparisons. A draft with explicit Start and Finish remains selectable after its old route is invalidated.

KML/KMZ point placemarks and GPX waypoints can also update protected control locations during protected controls/route import. The importer matches point or waypoint names to existing controls by SI code, control label, or public label, compares their latitude/longitude against encrypted protected coordinates, and applies only changed locations. KML/KMZ `LineString` objects and GPX route (`rte`) or track (`trk`) names are matched to Race File category names, and their points provide the imported route geometry. KML/KMZ `LineString` objects that appear to be decorative course circles are ignored: they must have more than 20 points, close back near their starting point, and have enough length that they are not simply duplicate points. If no course/route LineString is available in a Course Analyzer import, Radio-Oracle synthesizes a neutral `M21` route from Start through all recognized fox controls in normal control order, then beacon, then Finish before analysis begins. If a route object has no category indication, a single route is assumed to be `M21`; multiple unnamed route objects are assigned through existing older male categories first, then female categories, with missing fallback categories offered for creation. The import review warns about every category assumption before the imported data is made active. OCAD-specific GPX import/export conventions were not found in public documentation during implementation, so the current GPX support uses standard GPX 1.1 waypoints, routes, tracks, WGS84 latitude/longitude, and meter elevations as placeholders. Controls CSV import does not contain latitude/longitude fields, so it cannot update protected control locations.

## Algorithm Limits

Classic calculated-route search is exhaustive and currently limited to eight permuted course points. Sprint calculated-route search is exhaustive separately for the first and fast loops, with each loop capped at 120 permutations. Foxoring calculated-route search is exhaustive through six foxes; above six foxes, the analyzer uses the non-exhaustive hybrid search described above and states in the report that the Foxoring candidate was non-exhaustive.

The analyzer does not currently import map passability or symbol constraints. It does not know about out-of-bounds areas, dense vegetation, lakes, uncrossable creeks and rivers, cliffs, fences, walls, or other barriers and impediments to on-foot navigation. This limits both ideal-route selection and Classic wait-time estimates, because the true best route and actual arrival phases can differ from straight-line or imported-route geometry when terrain forces detours or slows travel. Future map-aware timing should preserve the category speed-factor table as one input and apply additional per-leg speed factors for vegetation, runnability, elevation change, barriers, and other mapped conditions.

## Reliable race/series workflow

1. Use Create Course, Move Course and Route Generator to establish the venue layout, then import the draft KML into Analyzer.
2. Analyze, adjust numbering or locations, and export/re-import the draft as often as needed. Save Race preserves each checkpoint. Partial imports remain drafts; review the import scope and unmatched categories.
3. Use Review and Apply Courses, confirm SI stations, prepare every course for the race, and apply. Repeat for each race day; different series members may use different designs.
4. Save and transfer with current desktop/Android builds. New files use Race File schema 7. Schemas 1–6 remain readable; older clients that only support schema 6 must not edit the new files.
5. Collect downloads against the applied assignments. To restart design before recording, edit a new draft and Apply again. After recording, use a revised race copy.
6. Export or publish from applied course data. When course diagrams are requested, missing or inconsistent courses stop publication. Choose results-only output intentionally when course data should be omitted. Generated replacement removes obsolete downloads and diagrams in that publication and preserves other races.

The bottom-right Unlocked/Locked indicator describes access to password-protected course data for the current session. It does not indicate design approval, race readiness, or whether a draft has been applied. Unlocking does not decrypt the saved file permanently. For plaintext course data, clicking Unlocked cannot lock it; use Race Password encryption to protect the saved data. The indicator has a tooltip explaining the applicable state.

## Automated acceptance tools

Use `just course-workflow-check` for the deterministic shared, desktop UI/export and Android regression gates. `just course-workflow-transfer-test` runs dependent desktop → archive → Android Room → archive → desktop phases with synthetic punches. Test app-data and preferences are isolated. These commands do not connect to a station or publish to a real destination.

`just course-audit <race-or-series>` is read-only. Locked data is reported as blocked. `just course-apply-preview <race-or-series> <design.json>` uses the production preparation service without saving. The design JSON contains `categoryId`, `bindingsByCategoryId` (category → placement → existing control ID), and an optional `kml` path relative to the JSON. For a series, use a top-level object keyed by race ID, with one such specification per race. No SI mapping is inferred by this tool.

`just course-export-verify <race-or-series> <new-output-directory>` generates KML, GPX, IOF CourseData and SVG files, checks exported placements, and parses XML. The separate `just iof-schema-check` gate validates the IOF schema. Preview/export CLI hooks currently require plaintext input; use the app for password-protected courses. Passwords and tokens are never command-line arguments.

`just course-publication-manifest <site-directory> <new-inventory.json>` validates public files and links and records their sizes and content hashes. Keep this inventory outside the public site. `just course-publication-verify <https-site-root> <inventory.json>` independently downloads those artifacts with cache-bypass requests. Missing or stale bytes fail verification. Publication itself uses the same byte verification after upload. If the provider accepts a deployment but verification fails, the error identifies that distinction; the provider may already have changed the public site, while the previous local mirror is retained.

Workflow reports use passed/failed/blocked/skipped. Audit and acceptance failures return nonzero; skipped device, terrain or remote checks never count as acceptance passes. See [implementation evidence](course-workflow-implementation-status.md) for the actual gates run on the current candidate.
